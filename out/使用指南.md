# eve Software Factory Template (Foreman) - 使用指南

> 生成时间: 2026-09-30
> 依据: README.md, .env.example, .github/ARCHITECTURE.md, package.json

## 1. 快速开始

### 1.1 环境要求

| 要求 | 版本 / 说明 |
|------|------|
| Node.js | 24.x (engines 钉死) |
| 包管理器 | pnpm (仓库带 pnpm-lock.yaml 与 pnpm-workspace.yaml) |
| Vercel 账号 | 生产部署与 Connect 连接器所需 |
| GitHub App | 经 Vercel Connect 授权,需安装到 `FACTORY_REPO` 且有 contents/issues/pull requests 写权限 |
| Linear (可选) | Agent Sessions 进件才需要 |
| 模型提供商 | `pnpm dev` 后在 TUI 运行 `/model` 链接一次;生产走 Vercel AI Gateway (项目 OIDC) |

### 1.2 一键部署(推荐)

点击 README 中的 Deploy to Vercel 按钮,部署流会自动配置:GitHub 连接器、Linear 连接器、Vercel Blob store(public 读),并提示填写 `FACTORY_REPO` 与 `FACTORY_LABEL` 环境变量。

两件事必须对齐才能真正干活:

- `FACTORY_REPO` 必须是 `owner/repo` 格式的真实仓库。
- 所选 GitHub App 必须安装并有该仓库的访问权。站点沙箱在**首个任务的首个会话**才克隆仓库(不在部署期),所以 App 够不着仓库时,报错形态是第一个任务上的 `Cannot access <owner/repo>`,而不是部署失败;装好 App 或改正值后重试即可。

### 1.3 本地开发

```bash
git clone <本仓库> && cd eve-software-factory-template
pnpm install
vercel link         # 关联你部署的项目 (或新建一个)
vercel env pull     # 拉取环境变量,含 Connect 与沙箱所需的短期 OIDC token
pnpm dev            # 启动 eve TUI;首次运行 /model 链接模型提供商
```

在 TUI 里直接派活(例如 "users report the password reset email arrives twice, fix it"),观察四个站点按序触发,最终在 `FACTORY_REPO` 上出现一个草稿 PR。本地运行的 dev principal 按设计不受信,所以对 GitHub 的改动会以审批卡形式等你批准。

想让本地 TUI 连到远端部署的 webhook 面:`eve remote connect --url <url>`。

## 2. 配置说明

### 2.1 环境变量(.env.example)

| 变量 | 必需 | 默认值 | 说明 |
|------|------|--------|------|
| `FACTORY_REPO` | 是 | — | 工厂服务的目标仓库,`owner/repo` 格式;模块加载期正则校验,缺失或畸形会让发现期直接失败 |
| `GITHUB_CONNECTOR` | 是 | — | GitHub 连接器 UID,部署按钮自动写入;手动建用 `vercel connect create` |
| `LINEAR_CONNECTOR` | 是(用 Linear 时) | — | Linear 连接器 UID |
| `FACTORY_SETUP_COMMAND` | 否 | — | 每次站点会话在克隆目录内执行一次(如 `pnpm install`),让仓库自检可跑 |
| `FACTORY_LABEL` | 否 | `factory` | 触发无人值守流水线的 issue 标签 |
| `FACTORY_BRANCH_PREFIX` | 否 | `factory/` | 工厂自有分支前缀;只有该前缀 PR 的红 CI 会触发自动修复 |
| `FACTORY_BOT_NAME` | 否 | 连接器解析的 App slug | @提及名;留空自动解析 |

注意:改动 `FACTORY_BRANCH_PREFIX` 时,implementer 的提示词里写死了默认前缀的说明(`agent/subagents/implementer/instructions.md`),保持两者同步。

### 2.2 常用命令

| 命令 | 作用 |
|------|------|
| `pnpm dev` | 本地 TUI 运行同一运行时 |
| `pnpm build` | `eve build` 构建期编译(提示词在此期注入 FACTORY_REPO) |
| `pnpm check` / `pnpm fix` | Ultracite (Biome) 检查 / 自动修复 |
| `pnpm typecheck` | tsc 严格类型检查 |
| `npx eve info` | 打印发现的面 + 发现期诊断(必须 0 错误 0 警告) |
| `pnpm validate` | check + typecheck + eve info 一条龙 |
| `pnpm eval --tag fast` | 便宜评测环(路由与安全,花真实 token) |
| `pnpm eval pipeline/full-pipeline` | 真跑全流水线并**推送真实分支**,只对 scratch 仓库刻意运行 |
| `eve deploy` | 部署到 Vercel 生产(不要用裸 `vercel deploy`,它无法自动识别 eve 框架) |

## 3. 主要功能(工作如何进来)

### 3.1 给 issue 打 `factory` 标签(无人值守)

**说明**: 打标签的人需要 ≥ triage 权限(钩子会实时校验)。流水线自动跑完,站点每完成一步在 issue 上发进度评论,最终交付关联该 issue 的草稿 PR。若 classifier 判定需澄清,会把问题评论在 issue 上然后停下,等回答后重新打标签再跑。

**使用**: 在目标仓库的 issue 上打 `factory` 标签,然后等通知。

### 3.2 @提及(交互式)

**说明**: 在 issue 或 PR 评论中 @ 机器人名;仅 OWNER/MEMBER/COLLABORATOR 的提及会开启会话。你在另一端回答澄清问题;可逆写直接执行,出货动作(标记 ready 等)停卡等你批准。

### 3.3 Linear 委派

**说明**: Linear Agent Sessions 走同一流水线,进度以 Agent Activities 报告,PR 链接回报到会话。工作区成员资格即门槛,会话全程 trusted。

### 3.4 红 CI 自动修复

**说明**: 工厂自己的 PR(`factory/*` 分支)上 CI 失败时,自动诊断并推送修复到同一分支;最多 2 次尝试,超过则把问题交还给人。别人推的分支永远不会触发。

### 3.5 本地 TUI 派活

**说明**: 见 1.3。审批卡浮在 TUI 里,是体验整个审批流的最快方式。

### 3.6 新 PR 导览评论

**说明**: 任何人开 PR(非 bot),工厂会在 PR 上发一条面向审查者的摘要评论(含变更文件表),只导览不审查。

## 4. 产出物与人类判断位

- **产出**: 草稿 PR,正文由流水线输出组装:问题陈述、方案及理由、验收标准清单(附 reviewer 逐条 pass/fail)、验证命令与结果、计划偏差、"Closes #N"。
- **人类判断位**: 标记 PR ready 属于人(任何调用者都停卡);合并不在工具面里,机器人从架构上无法合并;关闭/重开 issue 视为可逆分诊放行。
- **工厂大脑**: 每次运行从共享大脑起步(构建怪癖、验证陷阱、复现的审查发现、仓库约定)。受信运行可把验证过的持久事实写回大脑;无人值守运行只能在自己收尾回复里建议一条"Suggested factory brain note",等维护者确认。
- **用户偏好**: 交互会话开头自动加载你保存的长期偏好(默认基分支、PR 描述结构偏好、默认 Linear 团队),key 派生自登录主体,跨会话生效。

## 5. 二次开发速查

| 想改什么 | 去哪里 |
|------|------|
| 换某个角色的模型 | `agent/lib/models.ts` 的 `MODELS` 一行(implementer 与 reviewer 保持不同厂商) |
| 改编排流程/文风 | `agent/instructions.ts`(构建期注入 FACTORY_REPO) |
| 改某站点行为 | `agent/subagents/<id>/instructions.md` |
| 调授权策略 | `agent/lib/github/approval.ts`(不要在别处新造调用者检查) |
| 加 Blob 保留前缀 | `agent/lib/blob.ts` 注册表 |
| 加扩展工具白名单 | `agent/extensions/github.ts` 的 include 列表 |
| 评测 | `evals/` 一文件一用例;标签 `fast` / `slow` / `needs-connect` / `pipeline` |

提交前检查清单(来自 AGENTS.md):`pnpm validate` 全绿;不提交 secrets、`node_modules`、构建产物(`.eve`、`.vercel`、`.output`)。

## 6. 常见问题

### Q: 部署成功了,第一个任务却报 "Cannot access <owner/repo>"?
A: GitHub App 没有安装到 `FACTORY_REPO`(或 `FACTORY_REPO` 值不对)。站点沙箱在首个会话才克隆仓库,所以问题延迟到首次任务暴露。安装 App 到该仓库后重试。

### Q: 打了标签但没反应?
A: 依次确认:(1) 标签者对该仓库 ≥ triage 权限(建 issue 时自带的标签也会触发钩子,钩子会校验标签者权限并拒绝低权限);(2) 标签名与 `FACTORY_LABEL` 一致;(3) webhook 订阅了 `issues` 事件且指向 `/eve/v1/github`。

### Q: @提及没反应?
A: 提及者的 `author_association` 必须是 OWNER/MEMBER/COLLABORATOR;CONTRIBUTOR 及以下的提及只被确认、不派发。这是刻意的门禁。

### Q: 无人值守运行为什么不问我要批准?
A: 设计如此:无人值守会话没人看审批卡,所以策略对它们返回 denied(服务端一步)而不是挂起。自治运行只被允许:打标签、评论自己的进件 issue、关/重开 issue、开草稿 PR。

### Q: 本地 `pnpm dev` 需要本地 Docker 或 Linux 沙箱吗?
A: 不需要。站点沙箱是云端 Vercel Sandbox;本地只需 Node 24 + pnpm,`vercel env pull` 提供短期 OIDC token 即可。

### Q: 机器人会合并我的 PR 吗?
A: 不会。合并工具不在工具面里;标记 ready 对所有调用者(包括受信的)都停卡等人。

### Q: 评测会花钱吗?
A: 会,评测消耗真实模型 token。`--tag fast` 是便宜的环;`pipeline/full-pipeline` 会推真实分支,只对 scratch 仓库运行。
